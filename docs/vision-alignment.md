# requirements と仕様を vision.md に合わせるための仕分け（下書き）

この文書は、requirements.md と docs/specs/ の各節を docs/vision.md に照らして仕分けた結果である。本人が下の「決めてほしいこと」に答えたあと、この仕分けに沿って requirements と仕様を書き直す。書き直しが終わったら、この文書は消すか、移行の記録として残す。

区分は次の4つである。

- **残す**: Evaloom の管轄で、いまの書き方のままでよい。
- **一般化**: Evaloom の管轄だが、開発の仕事を前提に書いてある（Project は Git リポジトリ、出すものは PR、確かめるのはテスト、など）。
- **移す**: 開発ハーネス（software-engineer）の中身。一覧は `~/workspace/harnesses/software-engineer/docs/design.md` に写す。
- **契約**: Evaloom とハーネスの約束として、ハーネス契約の文書に切り出す。

## 1. 仕事が入ってから返るまで（書き直し後の形）

vision.md 4章の基準により、仕様を確定する前に本人に見せる流れ図である。

```
Linear の Issue（ai-ready）／管理画面での手動作成
   │
   ▼
[1 入る] Evaloom が定期照会で取り込む
   │
   ▼
[2 振り分ける] Evaloom
   ├─ 振り分けの表にあるラベルがちょうど1つ → 振り分け先（Project またはハーネス）が決まる
   └─ ラベルが無い・知らない・2つ以上
        → AI が Issue を読み、鍵の無い隔離の中で振り分け先を1つ提案する
        → Linear に提案をコメントする
        → 本人が承認する（Linear で提案のラベルを付ける、または管理画面で承認する）
        → 承認されるまで実行しない
   │
   ▼
[3 順番待ち] Evaloom（全体2本、振り分け先ごとに1本。ハーネスの版をここで固定）
   │
   ▼  ここからハーネスの中身。Evaloom は段ごとに隔離した場所を用意する
[4 作業する]   作業中の AI。鍵は無い。ネットワークはモデルの API だけ
   │
   ▼
[5 確かめる]   ハーネスの固定した版のコードと基準で確かめる。作業中の AI が書いたものは使わない
   │            確かめた成果物の識別子（ハッシュ）を Evaloom が記録する
   ▼
[7 承認する]   ハーネスが「承認が要る」と宣言した操作だけ、Evaloom の画面で本人が承認する
   │            承認は成果物の識別子に結び付く。中身が変わったら承認は無効になる
   ▼
[6 出す]       Evaloom が鍵をこの段にだけ渡す。直前に中止と承認を Evaloom に問い合わせる
   │            出す成果物の識別子が、確かめたものと一致しなければ出さない
   ▼
[8 返す] Evaloom: Linear へのコメントと状態の変更、通知、管理画面、記録。
         ハーネスの記録を残し、同じハーネスの次の仕事に参考として渡す
```

開発の仕事なら、4 は worktree での実装と commit、5 はテスト（いまの Gate 2・3）、6 は push と PR 作成、7 は PR のマージになる。どれも software-engineer の中に置く。

## 3. ハーネス契約に入れるもの

正本は `docs/contract/harness-contract-v1.md`（新設）に置き、版を付ける。ハーネスを作る人は、この文書だけを読めば作れるようにする。

1. 契約の版と、ハーネスリポジトリの形（`evaloom/profile.yaml` など Evaloom が読むもの）。タグ `profile/v<SemVer>`、公開済みタグの付け替え禁止
2. 宣言する項目: 段ごとのコマンド・上限時間・ネットワークの許可宛先・出力、受け入れ条件の要否、承認が要る操作と外してよい承認、Project から受け取る値のスキーマ、記録として残すもの
3. HarnessRequest と HarnessResult の汎用の形、エラー分類、確かめた結果（finding）の形
4. 作業段から見える範囲（専用設定環境、本人の設定を読まない、鍵は無い、Control API と DB に届かない）
5. 確かめる段の義務（固定した版から読む、作業中の AI が書いたものを使わない、自己申告を使わない）
6. 成果物の識別子と照合（確かめたもの＝出すもの、承認との結び付け）
7. 出す段の義務（直前の問い合わせ、Fail Closed、鍵をログやファイルに書かない、結果が分からないときの扱い）
8. 承認要求の形と consume の使い方
9. 記録の受け取り方（読み取り専用、指示ではなく参考資料）と、Issue 本文を外から来た文として扱うこと
10. 中止、タイムアウト、続け直し（continue と fresh）

## 5. 決めてほしいこと

推奨を先頭に書いた。

1. **いま動いている実装と仕様の関係。** 【2026-11-10 本人決定: B】全部を目標の形に書き直す。06・10・11 の中身は software-engineer 側の文書へ移し、evaloom からは消す。理由: 現状は何も運用で動いていないため、切り替えまでの説明を evaloom に残す必要が無い。
2. **振り分けのキー。** 【2026-11-10 本人決定: A】ラベルだけで決める。Team の概念は振り分けに使わない。理由: Issue はずっと同じところに登録し続けるため。Evaloom が照会する先は全体設定に1つ持つだけにする。
3. **Linear での承認の範囲。** 【2026-11-10 本人決定】本人が判断する場面（振り分けの承認、操作の承認、止まった仕事の続行）は、すべて管理画面の1か所で受け付ける。Linear は知らせるだけにする（「管理画面で判断待ち」のコメントとリンク）。Linear で本人がラベルを付けるのは承認ではなく、普通の振り分けとして扱う。管理画面で判断した結果は Evaloom が Linear に書き戻す（振り分けを承認したら振り分けのラベルを付けて状態を変える、など）。Evaloom が触ってよいラベルは振り分けのラベルだけで、`ai-ready` には触らない（起動の合図を自分で作らないため。16 の 3.5）。vision.md 2 章の「承認は管理画面でも Linear でも受け付ける」と食い違うため、vision.md の書き換えが要る（vision を変えてよいのは本人だけ）。
4. **出す段で動くコード。** 【2026-11-10 本人決定: A】鍵を受け取る出す段は、決まった手順だけを行うプログラムに限る。ハーネスの固定した版のコードを、作業段とは別の隔離で動かす。出す段ではモデルを呼ばない。文章を考えるなど AI の仕事は、鍵の無い作業段で済ませておく。
5. **確かめたもの＝出すもの（いまの Gate 3）を誰が保証するか。** 【2026-11-10 本人決定: B】ハーネスの中で見張る。Evaloom は確かめた段と出す段の照合をしない。ただし承認と中身の結び付け（17、requirements 15.8、受け入れ条件22）は承認の仕組みとして Evaloom に残す。承認要求でハーネスが渡す内容の識別子と、出す直前にハーネスが送る識別子を Evaloom が比べ、違えば承認は無効にする。
6. **Project が4項目のほかに持つもの。** 【2026-11-10 本人決定: C】承認を省く設定（承認ポリシー）と、動かすマシンの指定（Runner）の両方を Project に持たせる。vision.md 3 章の「4つだけ」に2つ足す書き換えが要る（vision を変えてよいのは本人だけ）。
7. **準備の段。** 【2026-11-10 本人決定: A】ハーネスが任意で宣言できる「準備の段」を足す。段は 準備（任意）→ 作業 → 確かめる → 出す。準備の段は AI を使わないプログラムだけで動かし、Evaloom は読み取り用の鍵と、ハーネスが宣言した接続先だけを渡す。作業段には鍵も外への接続も渡さない（モデルの API を除く）。
8. **用語。** 【2026-11-10 本人決定】3層で呼び分ける。Evaloom＝マクロハーネス、software-engineer など仕事の種類ごとのやり方一式＝スペシャルハーネス、Claude Code・Codex＝ミクロハーネス。仕様では単に「ハーネス」と書かず、必ず「スペシャルハーネス」「ミクロハーネス」と書き分ける。Evaloom は仕様の中では「Evaloom」と書き、「マクロハーネス」は層の関係を説明するところ（vision.md、用語の表）で使う。

このほか、次は推奨どおりに直す予定である。受け入れ条件を必須にするかはハーネスが宣言する。同時実行は振り分け先ごとに1本、全体2本のままにする。Project Context はハーネスが固定して報告する文脈として記録だけ残す。requirements 20 章の条件12・15・18 は software-engineer の受け入れ条件へ移し、Evaloom 側は契約に合っているかのテストに置き換える。評価と改善（requirements 10〜13 章）は将来の Phase として残す。

## 6. 書き直しで足すこと（相談の中で出たもの）

- 作業中の AI が判断できないことを質問として結果に書いて終わったら、Evaloom はその仕事を「本人の判断待ち」にし、管理画面に質問を出す。本人が答えたら、同じセッションを再開して答えを渡す（`claude -p --resume` など）。04 の「Blocked からの続行」とハーネス契約に足す。判断の場所は 5 章 3 の決定どおり管理画面だけ。
- 承認の結び付けの流れ（2026-11-10 本人確認）: ハーネスが識別子つきで承認を求める → Evaloom が管理画面に出す → 本人が判断 → Evaloom が結果を返す → ハーネスが出す直前に識別子を送り直す → Evaloom が承認時と比べ、違えば無効にする。
