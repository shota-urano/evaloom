# 1. プロジェクト概要

## 1.1 システム名称

**Evaloom（エヴァルーム）**

Evaluate（評価）とLoom（織り合わせる）を組み合わせた名称。

仕事の種類ごとのスペシャルハーネスを連携させ、実行結果を評価しながら継続的に改善するAI組織を表す。

## 1.2 目的

Evaloom は、Linear などから仕事を受け取り、どの Project またはスペシャルハーネスに頼むかを決めて振り分け、結果を返すオーケストラである。仕事そのもの（準備し、作業し、確かめ、出す）はスペシャルハーネスが行う（vision.md 1章）。

開発の仕事だけを扱うものではない。開発、X の運用、調査など、種類の違う仕事を同じ仕組みで扱う。

仕事を動かす仕組みは、次の3つの層に分かれる（vision.md 2章）。この文書では、単に「ハーネス」とは書かず、必ず「スペシャルハーネス」か「ミクロハーネス」と書き分ける。

| 呼び名 | 指すもの | 役目 |
|---|---|---|
| マクロハーネス | Evaloom | 仕事を受け取り、振り分け、順番を待たせ、本人の判断を取り、結果を返す |
| スペシャルハーネス | software-engineer など、仕事の種類ごとのやり方一式 | 指示、スキル、準備・確かめる・出すのプログラムを持ち、仕事の中身をこなす |
| ミクロハーネス | Claude Code、Codex | 指示を受けて、実際に考えて手を動かす AI の道具 |

Evaloom は、次を統合的に管理する。

- 仕事の受け取り（Linear、管理画面からの手動作成）
- 振り分け（Issue のラベル、決まらないときは AI の提案と本人の承認）
- 順番待ちと同時実行の制御、タスクの状態管理
- スペシャルハーネスの登録と版の固定
- 段ごとの安全な場所（隔離、鍵の保管と受け渡し、固定した版からの読み出し）
- 本人の判断（振り分けの承認、操作の承認、止まった仕事の続行、作業中の AI の質問への回答）を管理画面の1か所で受け付けること
- 結果の返却（Linear へのコメントと状態の変更、通知、管理画面、記録）
- コンテキスト管理
- ハーネス契約と中央テスト
- 分野別の定量評価、継続的な自己改善、モデル更新に応じた最適化（後の Phase）
- バージョン管理・承認・ロールバック

最終的には、各スペシャルハーネスが独立して仕事をこなしながら、Evaloom が振り分け、本人の判断、品質と改善を統制するAI組織の実現を目指す。

## 1.3 基本原則

1. Evaloom は、仕事の受け取り、振り分け、順番待ち、本人の判断、結果の返却を統括する。仕事の中身はスペシャルハーネスが行う。評価と改善は後の Phase で Evaloom が統括する。
2. スペシャルハーネスは、Evaloom とは独立したリポジトリとして管理する。Project はリポジトリを持たないこともある。リポジトリを持たない仕事は、スペシャルハーネスへ直接振り分ける。業務プロジェクトのリポジトリは、それを扱うスペシャルハーネスが、Project の渡す値として受け取る。
3. 複数の Project から同じスペシャルハーネスを共有できる。
4. Project ごとに、頼むスペシャルハーネスの Profile の版を固定できる。スペシャルハーネスへ直接振り分けた仕事では、そのスペシャルハーネスの既定の版を使う。
5. ハーネス契約と評価基準には明確な正本を設ける。ハーネス契約の正本は `docs/contract/harness-contract-v1.md` とし、版を付ける。
6. すべての正式運用のスペシャルハーネスは評価仕様を持つ。評価基盤ができるまでのスペシャルハーネスは「暫定運用」として扱う（11.1）。
7. 改善案は比較実験と実運用データに基づいて採用する。
8. AI同士の協議は必要な場合のみ実行する。
9. コンテキストは責務ごとに分離し、必要な情報だけを渡す。
10. 重要操作は権限制御・監査・承認を必要とする。本人の判断は管理画面だけで受け付ける。
11. 新しい種類の仕事、新しいスペシャルハーネス、新しいミクロハーネスやモデルを足しても、Evaloom の中心（受け取り、振り分け、順番待ち、本人の判断、返却）を変えない。変えてよいのは登録処理だけとする（20章の条件31）。
12. 評価不能な変更を自動的に本番適用しない。
13. 危険な操作は、AIへの禁止指示ではなく、AIの権限外に置くことで防ぐ。例えば「PRをマージしない」と指示するのではなく、AI が動く作業の段にマージの鍵を渡さない。
14. AIが実行するコードだけでなく、AIが書き換えられるコードも信用しない（15.7）。
15. 実行・改善するAIと、その合否を決める仕組みを分ける。AIが合格基準を自分で変えて合格できる状態を作らない。合否は、スペシャルハーネスの固定した版の確かめる段だけで決める（ハーネス契約 12章、11.6、12.3）。
16. 安全対策は、対象となるリスクと防止効果を明確にし、リスクの重大性と実装・運用コストを比較したうえで、必要十分な範囲で設計する。重大なリスクへの必須対策は省略しない。
17. 仕事の種類で中身が変わる処理は、スペシャルハーネスに置く。変わらない処理を Evaloom に置く（vision.md 5章）。モデルが起こす失敗への対策も、各スペシャルハーネスの中で完結させる。
18. 振り分けは Issue のラベルで決める。ラベルで決まらないときは、AI が振り分け先を提案し、本人が管理画面で承認してから実行する。AI は提案するだけで、承認なしに実行を始めない。
19. 鍵を持つ段（準備と出す）は AI を呼ばない。スペシャルハーネスの決まった版のプログラムだけで動かす。文章を考えるなど AI の仕事は、鍵の無い作業の段で済ませておく。

# 2. システム全体構成

## 2.1 アーキテクチャ

Evaloomを以下のレイヤーで構成する。


| レイヤー                | 役割                                           |
| ------------------- | -------------------------------------------- |
| Event Layer         | 外部サービスや手動指示からのイベント受信                         |
| Control Layer       | 振り分け（ラベル、提案と承認）、順番待ち、権限                     |
| Registry Layer      | Project、スペシャルハーネスと Profile の版、振り分けの表、ミクロハーネスの Adapter、モデルの管理 |
| Context Layer       | Global / Harness / Task Context と、スペシャルハーネスが報告した文脈（reported）の管理 |
| Collaboration Layer | AI同士の協議、レビュー、成果物統合（後の Phase）                           |
| Execution Layer     | 段ごとの Sandbox の作成、鍵の受け渡し、ミクロハーネスの起動、実行監視、作業領域の管理 |
| Evaluation Layer    | ルーブリック評価、比較分析（後の Phase）                            |
| Improvement Layer   | 改善提案、実験、採用、ロールバック（後の Phase）                            |
| Management UI       | 監視、設定、本人の判断（振り分けの承認、操作の承認、続行、質問への回答）、履歴の表示 |


各レイヤーは責務を明確に分離する。

Evaloom は各スペシャルハーネスの具体的な実装に直接依存せず、ハーネス契約とミクロハーネスの Adapter を介して利用する。

## 2.2 技術スタック


| 領域         | 採用技術                       |
| ---------- | -------------------------- |
| フロントエンド    | React + Vite + TypeScript  |
| UI         | Tailwind CSS + shadcn/ui   |
| バックエンド     | Go                         |
| HTTP API   | Go標準 `net/http`            |
| リアルタイム通信   | Server-Sent Events（SSE）    |
| 初期データベース   | SQLite / WALモード            |
| 将来的なDB候補   | PostgreSQL                 |
| 非同期処理      | Go Worker + 永続ジョブ管理        |
| スペシャルハーネスとの接続 | ハーネス契約（Profile 定義、段の要求 JSON と結果 JSON） |
| ミクロハーネスの接続 | CLI / SDK / 外部プロトコルAdapter |
| ソースコード管理   | Git / GitHub（Evaloom 本体と、スペシャルハーネスの版の固定） |
| 作業環境       | 段ごとの Sandbox（準備・作業・確かめる・出す）と、タスクごとの作業領域 |
| 初期実行ホスト    | Mac mini M4 Pro            |
| バックグラウンド起動 | launchd                    |
| 利用範囲     | `127.0.0.1` で待ち受ける。別の端末からは Tailscale のネットワーク（tailnet）の中の `tailscale serve` の中継だけで届く。インターネットには公開しない（15.5、specs 18） |
| Linear取り込み | EvaloomからLinear APIへ一定間隔で照会する（ポーリング）。Mac miniのポートは公開しない |
| 通知         | Linearコメント＋macOS通知（将来Slack・スマートフォンを追加可能にする） |


ライブラリの具体的なバージョンは詳細設計時に検証して固定する。

## 2.3 デプロイ方針

初期段階では、React管理画面、Go API、Runner、SQLiteをMac mini上で稼働させる。

Goバックエンドは管理画面とは独立して常駐する。

将来の分散実行を考慮し、Runnerを論理的に独立したコンポーネントとして設計する。

RunnerはControl Planeへ自分から仕事を取りに行く方式（pull）とする。Control PlaneからRunnerへは接続しない。Runnerを別のマシンに置いても、外からRunnerへ接続する必要がない。

Control Planeを別サーバーへ移設しても、各Runnerの設定を更新することで実行先を切り替えられる構成とする。

# 3. GitHub・ディレクトリ管理

## 3.1 基本方針

Evaloom本体と各スペシャルハーネスは、原則として独立したGitHubリポジトリで管理する。業務プロジェクトのリポジトリは、それを扱うスペシャルハーネスが扱い、Evaloom は参照しない。

Evaloom の配下にすべてのリポジトリを配置する必要はない。

GitHub管理の対象は以下とする。

- ソースコード
- 仕様書
- 設計資料
- ハーネス契約
- プロンプト
- Skills
- テストコード
- 評価基準
- Profile 定義（スペシャルハーネスのリポジトリの `evaloom/profile.yaml`）
- 非機密の構成ファイル

以下は原則としてGitHubへコミットしない。

- APIキー
- 認証トークン
- 秘密鍵
- 実行中のSQLiteデータベース
- 機密性を含む実行ログ
- タスクの作業領域
- 顧客の秘密情報

必要な履歴はDBや別の適切なストレージに保存する。

## 3.2 推奨ディレクトリ構成

```
~/
├── evaloom/
│   ├── frontend/
│   ├── backend/
│   ├── evaluations/
│   ├── context/
│   ├── configs/
│   └── docs/
│       └── contract/        ハーネス契約の正本
│
├── harnesses/               スペシャルハーネスのリポジトリ
│   ├── software-engineer/
│   └── custom-research/
│
├── projects/                業務プロジェクトのリポジトリ（扱うのはスペシャルハーネス）
│   ├── customer-system/
│   ├── corporate-site/
│   └── internal-tool/
│
└── ai-workspaces/           Runner がタスクごとに作る作業領域のルート（Runner の設定で決める）
    ├── task-001/
    └── task-002/
```

これは推奨配置例であり、配置場所を強制しない。

既存プロジェクトの移動は不要とする。

## 3.3 パス管理

Evaloom は、各リソースを以下の情報で識別する。

- Project ID
- スペシャルハーネスの ID
- Runner ID
- Profile の版（SemVer と commit SHA）
- 振り分けのラベル

Project がスペシャルハーネスに渡す値（params）は、Evaloom にとって不透明な値である。中身（業務プロジェクトのリポジトリ、ベースブランチなど）を Evaloom は解釈しない。Profile が渡す値のスキーマを宣言していれば、Evaloom は形だけを確かめる（ハーネス契約 5.2、Q115）。

業務プロジェクトのローカルパスや Git リポジトリの存在確認、アクセス権限、Git リポジトリとしての妥当性の検証は、スペシャルハーネスが自分の段（主に準備の段）で行う。Evaloom が登録時に検証するのは、スペシャルハーネスのリポジトリとタグ、Runner の作業領域のルートだけである。

AIに実行先パスを推測させない。段に渡すパスは、Evaloom が要求 JSON で決めて渡す（ハーネス契約 6.1）。

## 3.4 リポジトリ間の依存関係

スペシャルハーネスを Project に適用する際、スペシャルハーネスのソースコードを業務プロジェクトのリポジトリにコピーしない。

Evaloom の Registry（Project、スペシャルハーネス、振り分けの表）によって参照関係を管理する。

使用する Profile は SemVer のバージョンで固定する。各バージョンには実体の Git commit SHA を記録する（5.4）。

共有するスペシャルハーネスの更新が、利用中のすべての Project へ無条件に反映されることを防ぐ。

# 4. Project・スペシャルハーネスの共有

## 4.1 目的

同じスペシャルハーネスを複数の Project から利用可能にする。

例えば、`custom-research`をProject AとProject Bの双方から利用できるようにする。

## 4.2 適用方式

Project には、頼むスペシャルハーネスを1つだけ関連付ける。役割ごとに複数のスペシャルハーネスを割り当てる方式（developer、researcher など）はやめた。別のスペシャルハーネスに頼みたい仕事は、別の Project を作るか、スペシャルハーネスへ直接振り分ける。

構成例

```
projectId: project-a
name: Project A
routeLabel: "route:project-a"       # 振り分けのラベル（6.2）
harnessId: software-engineer        # 頼むスペシャルハーネス
profileVersion: "1.2.0"             # 固定する版（4.3）
params:                             # スペシャルハーネスに渡す値。中身は Evaloom が解釈しない
  repository: owner/project-a
  baseBranch: develop
approvalWaivers: []                 # 承認を省く操作（15.3）
runnerId: mac-mini                  # 動かすマシン
```

これはEvaloom独自の設定仕様案である。`params` の形は、スペシャルハーネスが Profile 定義で宣言する（ハーネス契約 5.1）。

実行時、Evaloom は固定した版の Profile を読み出し、段ごとの Sandbox を用意して、スペシャルハーネスの段を動かす。

## 4.3 バージョン固定

Project ごとに使用する Profile の版を固定できる。

例


| Project    | スペシャルハーネス             | Profile |
| --------- | ---------------- | ------- |
| Project A | software-engineer | 1.2.0   |
| Project B | software-engineer | 1.3.0   |
| Project C | custom-research  | 2.0.0   |
| Project D | custom-research  | 1.8.0   |


新しいProfileは既存Profileを上書きせず、独立した変更候補として管理する。新しい版を登録しても、Project の版は自動では変わらない。

## 4.4 スペシャルハーネスの更新

共有するスペシャルハーネスが改善された場合、以下を実行する。

1. 新しい版のタグを付ける（`profile/v<SemVer>`、ハーネス契約 4.2）
2. ハーネス契約への適合テスト
3. スペシャルハーネス固有のテスト
4. 影響する Project の検出
5. 代表の Project による検証
6. 必要に応じて14日間の評価
7. 採用判断
8. Project ごとの Profile の版の更新

影響する Project への無条件な一括反映は禁止する。

# 5. Registry管理

## 5.1 Project Registry

Project が持つのは、次の6項目だけとする（vision.md 4章、本人決定 6）。

- 名前
- 振り分けのラベル
- 頼むスペシャルハーネス（と固定する Profile の版）
- そのスペシャルハーネスに渡す値（中身は Evaloom が解釈しない）
- 承認を省く設定（どの承認を省くか）
- 動かすマシン（Runner）の指定

ローカルのパス、Git の URL、ベースブランチ、Linear Team、テストコマンド、セットアップコマンド、作業領域へコピーするファイルの許可リスト、Context の置き場所、許可操作は、Project に持たない。仕事の種類に固有の情報であり、必要ならスペシャルハーネスが渡す値として受け取るか、自分で持つ（開発の場合は software-engineer が持つ）。テーブルの形は specs 02 の projects と routes に従う。

## 5.2 Harness Registry（スペシャルハーネスの登録）

Evaloom が登録として持つのは次のとおりとする。

- スペシャルハーネスの ID
- 名称
- リポジトリの URL と、Control Plane と Runner が読むローカルの複製
- 既定の版（スペシャルハーネスへ直接振り分けた仕事で使う Profile）
- 登録した Profile の版（5.4）

スペシャルハーネスは、版ごとに次を Profile 定義で宣言する（ハーネス契約 5章）。Evaloom はこの宣言を読み、段と安全な場所を用意する。

- 段: 準備（任意）・作業・確かめる・出すの各段のコマンド、上限時間、外への接続の許可宛先
- 承認対象: 本人の承認が要る操作と、Project の設定で承認を省いてよいか（`waivable`）
- 鍵: 段ごとに要る鍵の名前と使い方（準備は読み取り用だけ、出すは読み取りと書き込み）
- 受け入れ条件の要否（`required` / `optional`）
- params のスキーマ（Project から受け取る値の形）
- 作業の段のミクロハーネス、モデル、指示・スキル・設定、Tool Permissions
- 記録として残すもの

専門分野、対応タスクは Profile 定義の `description` に書く（振り分けの提案に使う）。Evaluation Policy と Improvement History は、評価・改善の Phase で足す。

## 5.3 Model Registry

保持情報

- Provider
- 正式なModel ID
- 対応する実行環境
- コンテキスト制限
- ツール利用能力
- 推論設定
- 料金情報
- 公式参照元
- 確認日時
- 対応Harness Profile

モデルの表示名と実際のModel IDを区別する。

作業の段で使う Model ID の正本は、当面 Profile 定義の `stages.work.model` とする。Model Registry は Model Intelligence（13章）と合わせて後の Phase で作る（Q192）。

## 5.4 Harness Profile

Harness Profile は、スペシャルハーネスのある版の宣言（`evaloom/profile.yaml`）と、その版の commit の中身である（ハーネス契約 0章、5章）。

Evaloom が読むのは Profile 定義の宣言だけである。指示、プロンプト、スキル、準備・確かめる・出すのプログラムの中身を、Evaloom は解釈しない。指示・スキル・設定は、宣言どおりに作業の段の専用設定環境へ置くだけで、プログラムは宣言どおりに段の Sandbox で動かすだけである。

モデルが異なれば、同じ仕事の種類であっても異なるProfileを設定できる。

### バージョンと再現性

- Profileの表示バージョンにはSemVer（例 `1.2.0`）を使い、これを正本とする。
- 各バージョンの実体はGit commit SHAとともに記録する。
- 公開済みのタグの付け替えを禁止する。
- 同じProfileバージョンからは、常に同じ定義を読み込めるようにする。

### 状態

評価仕様を持たないProfileは「暫定運用」とし、評価仕様を備えた時点で正式運用へ移す（11.1）。

# 6. Linear連携

## 6.1 基本方針

Linear Projectを必須の識別子としない。

標準方式は、**Issue Label によるルーティング**とする。Linear の Team は振り分けに使わない（本人決定 2）。Issue はずっと同じところに登録し続けるため、Evaloom が照会する Team は全体設定（`linear.teamId`）に1つだけ持つ。

Linear は、仕事の入口と、知らせる先である。本人の判断（振り分けの承認、操作の承認、続行、質問への回答）は Linear では受け付けず、管理画面だけで受け付ける（本人決定 3）。Linear には「管理画面で判断待ち」と知らせ、管理画面へのリンクを載せる。

## 6.2 Label構成

推奨例

- `route:customer-system`（Project への振り分け）
- `route:research`（スペシャルハーネスへの直接の振り分け）
- `ai-ready`

振り分けのラベルは、全体設定 `linear.routingLabelPrefix`（既定 `route:`）で始まるラベルである（Q120）。振り分けのラベルから振り分け先を引く表（routes）を Evaloom が持つ。1つのラベルの振り分け先は、Project かスペシャルハーネスのどちらか一方である。

`ai-ready`が付与された時点を自動実行トリガーとする。`ai-ready`が付いたままのIssueが更新されても、再び起動しない。

`ai-ready`が外された場合、またはIssueがキャンセルされた場合は、そのIssueの待機中・実行中のタスクを中止する。

Evaloom が Linear に付けてよいラベルは、振り分けのラベルだけである。`ai-ready` には触らない（起動の合図を Evaloom が自分で作らないため）。

## 6.3 ルーティング処理

1. Linear API への定期照会（ポーリング）。照会先は全体設定の Team 1つ
2. `ai-ready`の付与・取り外しの検出（前回の照会結果との差分）
3. 重複排除（同じ付与から二重にタスクを作らない）
4. 振り分けのラベルの取得（接頭辞で始まるラベルだけを数える）
5. 振り分けの表との照合
6. 振り分けの表にあるラベルがちょうど1つなら、振り分け先が決まる。Task を生成し、実行キューへ登録する
7. ラベルが無い、表に無い、2つ以上のときは、Task を生成して振り分け待ち（`routing`）にする。AI が鍵の無い隔離（Proposal Sandbox）の中で Issue を読み、振り分けの表から振り分け先を1つ提案する。本人が管理画面で承認するまで実行しない
8. 本人が管理画面で振り分けを承認したら、Evaloom は Task を実行キューへ登録し、Linear にその振り分けのラベルを付け、状態を変える（書き戻し）

振り分けを待つ間に、本人が Linear で振り分けのラベルを1つだけ付けて振り分け先が決まったら、承認ではなく普通の振り分けとして扱う（提案は取り下げる）。

受け入れ条件の要否は、振り分け先のスペシャルハーネスが Profile 定義で宣言する（`acceptanceCriteria`）。`required` の振り分け先で受け入れ条件が書かれていないIssueは実行せずに保留し、Linearへ受け入れ条件の記入を求めるコメントを返す。`optional` の振り分け先では、受け入れ条件が無くても実行する。

詳細は specs 15（振り分けは 3.6、振り分けの提案は 3.6.4、受け入れ条件は 3.6.1）に従う。振り分け先が決まった後（`queued` 以降）にラベルが変わった場合の扱いは Q196。

## 6.4 実行結果の返却

処理完了後、該当Issueへ次の情報を返す。

- 実行ステータス
- 振り分け先（Project またはスペシャルハーネス）と Profile の版
- 作業概要（作業の段の `out/summary.md`）
- 確かめた結果の要約（確かめる段の `summary`）
- 外に出したもの（出す段の `outputs`。開発なら PR の URL）
- エラー情報
- 本人の判断待ち（「管理画面で判断待ち」と管理画面へのリンク）

Evaloom自身によるIssue更新が再び同じジョブを起動しないようにする。

管理画面で本人が判断した結果は、Evaloom が Linear に書き戻す（振り分けのラベルの追加、状態の変更）。詳細は specs 16（コメントは 3.2・3.3、状態の変更は 3.6、ラベルの追加は 3.6.5）に従う。

## 6.5 保存期間への配慮

LinearのIssue保存・アーカイブと料金プランによる制限を考慮する。

Linear Projectの使用を強制せず、Issueをタスク入力元として利用できる設計とする。

長期的な実行履歴と評価データはEvaloom側に保持し、Linearの保存状態へ依存しない。

Linearの料金枠・アーカイブ仕様は運用開始時に公式情報と実環境で確認する。

## 6.6 接続方式

- GraphQL APIの読み書きには個人APIキーを使う（Phase 2）。
- Linearの変化は、EvaloomがGraphQL APIへ一定間隔で照会して取得する（ポーリング）。Webhookは使わない。
- Mac miniのローカルHTTPポートは公開しない。Linearとの通信は、Mac miniから外へ向かうHTTPSだけで行う。
- 照会の間隔だけ取り込みが遅れることを許容する。Mac miniが止まっている間に付いた`ai-ready`は、再開後の照会で取り込む。

# 7. コンテキスト管理

## 7.1 階層構成

コンテキストは、Global・Harness・Task の3階層で管理し、スペシャルハーネスが報告した文脈を reported 層として記録する。

### Global Context

Evaloom全体の共通情報。

- 組織運用ルール
- ハーネス契約
- セキュリティポリシー
- 評価方針
- 権限・承認ルール

### Harness Context

スペシャルハーネス固有の情報。正本はスペシャルハーネスのリポジトリにあり、Profile の版に含まれる。

- 専門領域
- モデル向け指示
- プロンプト
- Skills
- ツール使用方針
- 得意・不得意な処理
- 過去の記録（同じスペシャルハーネスの前の仕事の記録、ハーネス契約 9章）

### Task Context

タスク固有の情報。

- Issue内容
- 受け入れ条件
- 実行状況
- 実行ログ
- 確かめた結果
- 未解決事項

### reported 層（スペシャルハーネスが固定して報告した文脈）

仕事の対象が持つ文脈（開発なら、業務プロジェクトのリポジトリの `AGENTS.md`、テスト仕様、コーディング規約）は、Evaloom では管理しない。スペシャルハーネスが準備の段で固定し、結果 JSON の `reportedContext` で報告したものを、Evaloom は記録して表示するだけとする（ハーネス契約 6.5、specs 02 の context_revisions）。

どのファイルを固定するか、作業の途中で変わったときにどう扱うかは、スペシャルハーネスが決める。開発の場合の `AGENTS.md` の固定の方法は software-engineer へ移した。

Evaloom は、ミクロハーネスの専用設定環境に置いた指示・スキル・設定（Profile の版から読んだもの）を、実行開始時の構成として記録する。

## 7.2 Context Builder

Evaloom が Context Builder を提供する。

実行時に必要な情報を抽出し、Execution Context を生成する。

処理には以下を含む。

- Context取得
- 関連情報の選択
- バージョン確認
- 優先順位判定
- 権限確認
- 情報量調整
- 実行先向けの整形

すべてのコンテキストを毎回渡すことは禁止する。

## 7.3 コンテキスト優先順位

Globalの安全・権限ルールは下位階層で上書きできない。

Harness Context と Task Context が矛盾した場合、情報の種類と権限に応じて解決する。reported 層の文脈と Harness Context の矛盾は、スペシャルハーネスが扱う。

解決できない重要な矛盾がある場合は実行せず、タスクを Blocked（本人の判断待ち、原因 `context_conflict`）にする。

## 7.4 Context更新管理

Evaloom が承認して反映する Context の更新は、Global Context に限る。

スペシャルハーネスの仕事の中で見つかった、Global Context への更新候補は、更新候補として提出する。Evaloom が根拠・既存情報との整合性・影響範囲を確認し、本人が承認したものだけを正式反映する。受け付け方は Q193。

Harness Context の更新は、スペシャルハーネスのリポジトリの変更として行い、新しい Profile の版として登録する（4.4）。Evaloom の承認は通さない。前の仕事の記録を次の仕事へ参考として渡すこと（ハーネス契約 9章）は、Context の更新ではない。

## 7.5 ミクロハーネスの設定環境の分離

Evaloom から起動するミクロハーネスには、作業の段ごとに専用の設定環境を設ける。置くのは、Profile の版で宣言した指示・スキル・設定だけである（ハーネス契約 6.3）。

本人のグローバル設定（`~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`など）や個人メモリを、意図せず読み込ませない。

ミクロハーネスが実際に読み込んだ指示を検証するテストを用意する（14.2）。

# 8. タスクオーケストレーション

## 8.1 イベント入力

初期対応

- React管理画面からの手動指示
- Linear（APIの定期照会）

仕事の種類は限定しない。開発、調査、X の運用など、振り分けの表にある振り分け先なら扱う。

管理画面から手動でタスクを作る場合は、振り分け先（Project かスペシャルハーネスの一方）を選ぶ。振り分け先の Profile が受け入れ条件を `required` と宣言していれば、受け入れ条件を必須の入力項目とする（6.3）。

将来的な対応

- Gmail
- GitHub
- Google Drive
- Slack
- Cron
- 外部API

## 8.2 タスク処理フロー

1件の仕事は、次の流れで進む（vision.md 3章）。

| 順 | 段・処理 | 中身 | 担当 |
|---|---|---|---|
| 1 | 入る | イベント受信、認証・重複排除、タスク生成 | Evaloom |
| 2 | 振り分け | ラベルで振り分け先を決める。決まらなければ AI の提案と本人の承認（6.3） | Evaloom |
| 3 | 順番待ち | 同時実行の制御（8.7）。Runner が取得した時点で Profile の版、渡す値、Context を固定する | Evaloom |
| 4 | prepare（準備、任意） | 作業に要るものをそろえる。AI を呼ばない。読み取り用の鍵と宣言した宛先だけ | スペシャルハーネス |
| 5 | work（作業） | ミクロハーネスが仕事の中身をこなす。鍵なし。外への接続はモデルの API だけ | スペシャルハーネス（ミクロハーネス） |
| 6 | check（確かめる） | 固定した版のプログラムで、結果が基準を満たすかを確かめる。中身の識別子（content_id）を報告する | スペシャルハーネス |
| 7 | 承認 | スペシャルハーネスが宣言した操作だけ、本人が管理画面で承認する | Evaloom |
| 8 | publish（出す） | 結果を外へ出す。AI を呼ばない。宣言した鍵と宛先だけ。外へ出す操作の直前に毎回 Evaloom に許可を問い合わせる | スペシャルハーネス |
| 9 | 返す | Linear へのコメントと状態の変更、通知、管理画面、記録 | Evaloom |

作業の段の AI が判断できないことを質問として書いて終わったら、Evaloom はタスクを本人の判断待ちにし、管理画面に質問を出す。本人が答えたら、同じセッションを再開して答えを渡す（ハーネス契約 8章）。

確かめる段が `blocked` を返したときと、出す段の結果がわからないときも、本人の判断待ちにする。続行は管理画面だけで受け付ける。

AI協議を導入するPhase 5までは、Collaboration ModeをSoloに固定する。

7の承認は、その操作を行う直前に承認を必須とし、事後承認にしない（15.3）。

タスクの分解（task_steps）はPhase 1では使わない。

段ごとの入力と結果の形、見える範囲はハーネス契約 6章に従う。

## 8.3 タスク状態

- Received
- Routing
- Queued
- Running
- Waiting Approval
- Blocked
- Completed
- Failed
- Cancelled
- Timed Out

値と遷移は specs 02 の 5.1 と 5.2 に従う。1.2 までの Planning と Verifying は使わない（Q119）。段ごとの細かい状態（準備中、作業中、確かめ中、出す段の実行中）は Execution の状態（`preparing` / `working` / `checking` / `publishing`）で表す。

ジョブの状態は永続化する。

再起動後も未完了タスクを検出できるようにする。

### 状態の扱い

- 振り分け先がラベルで決まらないタスクは、Blocked ではなく Routing にし、振り分けの提案と本人の承認を待つ（6.3）。
- 受け入れ条件が必須の振り分け先で、受け入れ条件のないタスクは、取り込みの保留として Blocked にする（6.3）。
- 本人の判断（止まった仕事の続行、作業中の AI の質問への回答）を待つタスクは Blocked にする。操作の承認を待つタスクは Waiting Approval にする。どちらも同時実行の枠に数えない。
- 1つのタスクに複数のExecutionを紐付けられる構成とする。再実行は、同じタスクに新しいExecutionを追加する。
- システム再起動で中断されたExecutionは失敗（中断、`interrupted`）として記録し、タスクをFailedにする。作業中だったタスクの作業領域は保持する。
- 中断・失敗したタスクを自動では再実行しない（自動リトライは0回）。本人が確認した後に、新しいExecutionを生成する。再実行では、前の作業領域を引き継ぐ（`continue`）か、新しい作業領域で始める（`fresh`）かを本人が選ぶ（ハーネス契約 10.3）。
- 使用するProfileの版、渡す値、Contextの版は、Runnerがタスクを取得した時点でExecutionに固定する。実行開始後に割り当てやContextが変わっても、そのExecutionでは切り替えない。
- 仕事の対象が持つ文脈（開発なら `AGENTS.md`）は、スペシャルハーネスが固定して報告する（7.1 reported 層）。

## 8.4 Local Runner

Mac mini上でスペシャルハーネスの段を動かすLocal Runnerを設ける。

Local RunnerはControl Planeから仕事を取りに行く（pull、2.3）。

役割

- 実行環境の確認
- タスクの作業領域の用意
- Profile の固定した版の読み出し
- 段ごとの Sandbox の作成と、段（prepare・work・check・publish）の起動
- 作業の段でのミクロハーネスの Adapter の起動
- 振り分けの提案の起動（Proposal Sandbox）
- 鍵の保管と受け渡し（準備の段には読み取り用だけ、出す段には宣言したもの。作業の段と確かめる段には渡さない）
- 段の通話口の中継（中止の確認、出す操作の直前の問い合わせ）
- プロセス監視
- ログ収集（渡した鍵の値を除外する）
- タイムアウト処理
- 実行キャンセル
- 成果物収集（段の `out`）
- 作業領域の後片付け

Runner は、push、PR の作成、マージなど、仕事の中身の操作を行わない。外への操作は、スペシャルハーネスの出す段のプログラムが行う。

## 8.5 Git作業の出口（software-engineer へ移した）

この節の中身（commit までと push・PR の分担、テストコマンドの正本、テストの弱体化への対策、Gate 2・3、検証と push の順序、ブランチ名、PR は最大1本、PR マージ、ベースブランチへの直接 push、再実行時のブランチ・PR の扱い）は、開発のスペシャルハーネス software-engineer へ移した（本人決定 1）。Evaloom 側に残る約束は、ハーネス契約に置いた。確かめる基準を作業前の固定版から読むこと（ハーネス契約 12章 2）、確かめたものと出すものが同じであることをスペシャルハーネスが見張ること（同 12章 3）、出す直前に Evaloom へ問い合わせること（同 7.4）、承認と中身の識別子の結び付け（同 7.2、15.8）である。

## 8.6 Worktreeの環境構築（software-engineer へ移した）

この節の中身（worktree の作成と開始点、セットアップコマンドの実行、コピー許可リスト）は、software-engineer へ移した（本人決定 1）。Evaloom が用意するのは、タスクの作業領域と、準備の段の Sandbox（読み取り用の鍵と宣言した宛先だけ）である（ハーネス契約 6.2）。

## 8.7 同時実行

- 同時に実行するタスクは全体で2本までとする。
- 同じ振り分け先（Project またはスペシャルハーネス）のタスクは1本ずつ実行する。
- 上限を超えたタスクはQueuedで待つ。
- 承認待ちと本人の判断待ちのタスクは、同時実行の枠に数えない。
- 振り分けの提案の数え方は specs 02 の Q111 に従う。

## 8.8 通知

- 本人の判断待ち（振り分けの承認、操作の承認、続行、質問への回答）が生まれたときに通知する。通知は知らせるだけで、判断は管理画面で受け付ける。
- 承認の仕組みが無いPhase 1では、タスクの完了と失敗を通知する。
- 初期段階の通知先はLinearコメントとmacOS通知とする。
- 将来的にSlackやスマートフォンへ届く通知経路を追加できる構成にする。

# 9. ミクロハーネスの Adapter

## 9.1 目的

異なるミクロハーネスを、作業の段で共通インターフェースで起動する。Adapter は、Evaloom とミクロハーネスの間に置くものであり、スペシャルハーネスとの約束（ハーネス契約）とは別である。

## 9.2 初期対象

- Codex
- Claude Code

将来的な追加候補（ミクロハーネス）

- Gemini CLI
- Factory Droid
- OpenClaw

調査、文書、ブラウザ操作などの仕事の種類は、Adapter ではなく、スペシャルハーネスとして足す。

## 9.3 共通機能

各Adapterは原則として以下を提供する。

- 実行要求受付
- 実行セッション識別
- ステータス取得
- ログ取得
- キャンセル
- 成果物返却
- エラー分類

再開やストリーミングなど、ミクロハーネスごとに異なる能力はCapabilityとして宣言する。

サポートしない能力を無理に共通化しない。

## 9.4 実行権限

Runnerは、タスクの作業領域の中でだけミクロハーネスを実行する。

作業の段の Sandbox で動かし、鍵を渡さず、外への接続はモデルの API だけにする（15.7）。

## 9.5 ハーネス契約

Evaloom とスペシャルハーネスの約束は、ハーネス契約（`docs/contract/harness-contract-v1.md`）を正本とする。スペシャルハーネスを作る人は、Evaloom の仕様全体ではなく、ハーネス契約の決まった版だけを読めば作れるようにする（原則5）。

| 区分 | 中身 | ハーネス契約 |
| --- | --- | --- |
| 宣言 | Profile 定義（段、承認対象、鍵、受け入れ条件の要否、params のスキーマ、記録） | 5章 |
| 入力 | 段ごとの要求 JSON（タスクの内容、振り分け先、渡す値、Profile の版、パス、前回の記録、承認、本人の回答） | 6.1 |
| 出力 | 段ごとの結果 JSON（状態、中身の識別子、要約、finding、承認の要求、外に出したもの、報告した文脈） | 6.5 |
| エラー分類 | `config_error`、`prepare_failed`、`work_failed`、`check_failed`、`publish_failed`、`publish_unknown`、`approval_rejected`、`contract_error`、`sandbox_error`、`timeout`、`cancelled`、`interrupted` | 13章 |

# 11. Evaluation System

## 11.1 基本方針

すべての正式Harness Profileに評価仕様を必須とする。

評価基盤ができるまで（Phase 1〜2）のProfileは「暫定運用」として扱い、評価仕様を備えた時点で正式運用へ移す。

評価は成功・失敗だけでなく、分野別の詳細な採点基準に従う。

1件ごとの合否は、スペシャルハーネスの確かめる段が決める。Evaloom の評価は、合否とは別に、分野別の採点と比較を行う（Q188）。

## 11.2 Developer評価例（software-engineer へ移した）

開発の仕事の採点の例（要件充足度、実装品質、テスト品質、安全性、作業効率、手順遵守の配点）は、software-engineer へ移した。分野ごとの採点基準の正本は、その分野のスペシャルハーネスが持つ。

各項目に0〜5の具体的な採点基準を定義する。

重大なセキュリティ違反は総合点とは別の失格条件とする。

## 11.3 分野別評価

以下の分野に独立した評価基準を設定する。

- Developer
- Researcher
- Reviewer
- Document
- Operations
- Planner
- Coordinator

異なる分野の総合点をそのまま比較しない。

Evaluation Agent（10.4）はReviewer分野に含める。

## 11.4 評価方法

- Unit Test
- Contract Test
- Integration Test
- E2E Test
- Regression Test
- LLM-as-a-Judge
- 人間による評価
- 実運用メトリクス

評価には実行証跡と根拠を保存する。

人間による評価は管理画面から入力する（16.5）。

## 11.5 評価AIの品質管理

評価AI自体の評価も実施する。

人間による基準評価との一致度、再現性、モデルによる偏りを測定する。

## 11.6 評価データの保護

- 評価基準と非公開テストデータは、改善担当からの書き込みを禁止する。
- 非公開テストの内容は、改善担当からの読み取りも原則として禁止する。
- 非公開テストデータは本人が過去のIssueから選んで作り、evaloomとは別の非公開リポジトリに置く。
- GitHubのブランチ保護、改善担当とは別の認証情報、Runnerのアクセス権限を組み合わせて、上記を強制する。
- 評価基準の変更には本人の承認を必須とする。

## 12.1 目的

- Adapter
- Context Policy
- Collaboration Policy
- タスク分解方法

## 12.3 改善フロー

1. 実行データ収集
2. 問題・傾向の検出
3. 改善仮説生成
4. 改善版Profile生成
5. オフラインテスト

## 12.5 比較指標

- 品質スコア
- 要件充足率
- 確かめる段の合格率
- 差し戻し率
- 実行時間
- 費用
- 手戻り
- 人間の修正負担
- 安全性
- 実行安定性

改善効果が十分に確認できない場合は判定保留とする。

### 指標の定義

下の差し戻し率・差し戻し回数・人間の修正負担は、開発の仕事（PR）での定義例である。仕事の種類ごとの定義はスペシャルハーネスが決める（Q189）。

| 指標 | 定義 |
| --- | --- |
| 差し戻し率 | レビューを受けたPRのうち、変更要求が発生したPRの割合 |
| 差し戻し回数 | PRごとの変更要求の回数 |
| 人間の修正負担 | 人間による追加修正コミット、その変更行数、手動介入の回数。可能なら実際の修正時間も記録する |
| 費用 | トークン数と実行時間で記録する。金額はAPI利用時だけ記録する |

変更行数だけでは修正負担を正確に測れないため、人間の修正負担は複数の指標で評価する。

どのProjectがどのProfileを使用していたかを追跡する。

正式採用後も旧版を保持し、ロールバック可能にする。

# 14. Central Test Coordinator

- 隔離突破テスト（段のプログラムや作業の段のコードに管理DBやControl APIへのアクセスを仕込み、段の Sandbox から実際にアクセスできないことの検証、15.7）
- Contract Test（ハーネス契約への適合。Profile 定義、要求 JSON、結果 JSON、出す直前の問い合わせ）
- Integration Test
- E2E Test
- Regression Test
- Evaluation Benchmark
- Improvement Experiment

## 14.3 テスト配置

試行回数、時間、費用の上限を設定し、無限ループを防ぐ。

# 15. Security &amp; Policy

## 15.1 基本方針

外部イベント・メール・Webページ・Issue本文を信頼済みシステム命令として扱わない。振り分けを提案する AI も、Issue の本文を外から来た文として読み、提案は本人の承認を通す。

セキュリティ設計では、次の原則を守る。

| 原則 | 内容 |
| --- | --- |
| Untrusted Code Execution | 作業の段が生成・変更できるもの（コード、ファイル）を動かす処理は、スペシャルハーネスのプログラムを含めて、段ごとの隔離環境で実行する（15.7） |
| Privilege Separation | 本人、Trusted Runner、段ごとの Sandbox の権限を分ける（15.5、15.7） |
| Approval Binding | 承認は、操作・対象・中身の識別子に結び付ける（15.8） |
| One-Time Authorization | 承認は原則として1回限りとする（15.8） |
| Fail Closed | 認証・承認・検証のどれかに失敗したら、操作を実行しない |

## 15.2 必須対策

- 外部からの受信口を公開しない（LinearはAPIの定期照会で取得する）
- イベント重複排除
- 循環トリガー防止
- 許可済み実行パス
- タスク単位の権限
- 実行環境の分離
- シークレット管理
- ログの機密情報除外
- タイムアウト
- 費用上限
- 監査ログ
- 重要操作の承認

## 15.3 承認対象

承認対象は、スペシャルハーネスの宣言と Evaloom の既定で決まる。

- スペシャルハーネスは、本人の承認が要る操作を Profile 定義の `approvals` に宣言する（ハーネス契約 5章、7章）。スペシャルハーネスを作るときは、戻せない外への操作（本番環境へのデプロイ、PR マージ、外部メール送信、重要ファイル削除、認証・権限変更など）を承認対象として宣言する。宣言の無い Profile の扱いは Q186。
- Evaloom の既定として、次の Evaloom 自身の変更は本人だけが行う（Q185）。ハーネス契約の変更、評価基準の変更、Evaloom 全体のセキュリティポリシーの変更、Project の承認を省く設定と Profile の版の変更。
- 宣言した操作は、既定で承認が要る。Project の承認を省く設定で省けるのは、スペシャルハーネスが `waivable: true` と宣言した操作だけである。スペシャルハーネスへ直接振り分けた仕事では、承認を省けない（Q113）。

承認は本人だけが、管理画面だけで行う。Linear のコメントやラベルは承認として扱わない（本人決定 3）。

承認対象操作は、その操作を行う直前に承認を必須とする。事後承認にはしない。出す段は、外へ出す操作の直前に毎回 Evaloom に問い合わせ、許可されたときだけ1回行う（ハーネス契約 7.4）。

権限と承認状態は、実行開始時だけでなく、副作用のある操作を実際に行う直前にも確認する。

承認の仕組みを導入するPhase 2までは、承認を求めた Execution は承認待ちのまま止め、出す段を始めない（Fail Closed）。これは指示で禁じるのではなく、Evaloom が出す段を起動しないことで止める。

ただし、Phase 1でも本人は、管理画面から Project の承認を省く設定と、Project に固定する Profile の版（Tool Permissions は版に含まれる、specs 02 の Q118）を変更できる。Runnerとスペシャルハーネスには、権限設定を変更する操作を許可しない。

## 15.4 Git作業環境（software-engineer へ移した）

worktree による作業環境の中身は、software-engineer へ移した（本人決定 1）。Evaloom が用意するのは、タスクの作業領域と段ごとの Sandbox である（15.7）。

## 15.5 利用者・認証・承認者

- 利用者は本人1人とする。Phase 1では利用者管理の仕組みを作らない。
- 利用者管理を作らないことと、タスクの実行権限を制限しないことは別である。タスク単位の実行権限の制限はPhase 1から必須とする（15.2）。
- 単一ユーザー運用は、外部からの無認証アクセスを許すという意味ではない。
- 管理画面とControl APIは、Mac miniのループバック（127.0.0.1）で待ち受ける。
- MacBook Air、スマートフォンなど別の端末からは、Tailscale のネットワーク（tailnet）の中の `tailscale serve` の中継だけで届く。Tailscale Funnel などのインターネットへの公開はしない（specs 18）。
- 本人は ID とパスワードでログインし、端末ごとのセッション（有効期限3日）を使う（specs 18）。
- 承認は本人だけが実施できるようにする。本人の判断（振り分けの承認、操作の承認、続行、質問への回答）は、管理画面だけで受け付ける。
- 本人・Trusted Runner・段ごとの Sandbox の権限境界を、正式な設計要件とする。
- 本人用APIは、ループバックと tailnet で届くため、同じマシンで動く不正なプログラムからのアクセスも考慮する。本人用APIには認証とCSRF対策を設ける。
- Runnerは、本人用とは別の限定された認証方式を使う。
- どの段の Sandbox にも、本人用とRunner用のどちらの認証情報も渡さない。

## 15.6 秘密情報の扱い

- 秘密情報はGitに含めない。
- スペシャルハーネスが外とやり取りするときに使う鍵（GitHub など）は、Evaloom が保管する。スペシャルハーネスは鍵の名前と使い方を宣言するだけで、鍵の値を持たない（ハーネス契約 11章）。
- Evaloom は、鍵を準備の段（読み取り用だけ）と出す段にだけ渡す。作業の段と確かめる段には、どの鍵も渡さない。管理用の認証情報だけでなく、業務プロジェクトのAPIキーや`.env`の中身も渡さない。
- 鍵を受け取る段（準備と出す）は、AI を呼ばない（原則19）。
- 鍵は Runner が保管し、Control Plane と管理 DB には値を置かない（specs 01 の 3.5）。
- テストに値が必要な場合は、テスト専用のダミーの値を使う。どの値を使うかはスペシャルハーネスが決める。
- 例外として、ミクロハーネスがモデルAPIへ接続するための認証情報がある。これはサンドボックスの外で付与し（認証を付けるプロキシなど）、ミクロハーネスから値が見えないようにすることを原則とする。CLIの仕組み上それができない場合に限り、Evaloom専用で、用途と利用上限を絞った認証情報を渡す。

## 15.7 実行権限の境界

Phase 1から、次の権限境界を必須とする。段ごとの見える範囲の正本はハーネス契約 6.2、構成要素の正本は specs 01 の 3.1 とする。

| 構成要素 | 実行内容 | 鍵 | 外への接続 |
| --- | --- | --- | --- |
| Control API | 本人用のAPIとRunner専用のAPIを分ける。それぞれ別の認証情報で操作する | スペシャルハーネスの鍵を持たない | Linear API |
| Trusted Runner | ジョブ管理、段ごとの隔離環境の作成、鍵の保管と受け渡し、通話口の中継 | 保管する | Control Plane |
| Prepare Sandbox | スペシャルハーネスの固定版の準備のプログラム。AI を呼ばない | 読み取り用だけ | 宣言した宛先だけ |
| Work Sandbox | ミクロハーネス（Codex・Claude Code）による作業。タスクの作業領域だけを編集できる | 無し | モデルの API だけ |
| Check Sandbox | スペシャルハーネスの固定版の確かめるプログラム。AI を呼ばない。作業領域は読むだけ | 無し | 無し |
| Publish Sandbox | スペシャルハーネスの固定版の出すプログラム。AI を呼ばない。作業領域は読むだけ | 宣言したもの | 宣言した宛先だけ |
| Proposal Sandbox | 振り分けの提案（AI が Issue を読む） | 無し | モデルの API だけ |

- `127.0.0.1`に限定しても、同じMac mini上の Sandbox からはHTTPリクエストを送れる。そのため、接続元の制限だけでは権限境界にならない。どの Sandbox からもホストのループバックへの通信を止める。
- 同じmacOSユーザーで動かす場合、APIトークンを別ファイルに置くだけでは隔離にならない。
- Runnerは、作業の段が書き換えられるもの（作業領域の中のスクリプトなど）をホスト上で直接実行しない。準備の段で依存関係をインストールするときも、段の Sandbox の中で行う。依存関係のインストール時に任意のスクリプトが実行される可能性があるためである。

### 隔離の条件

どの段の Sandbox にも、次の条件を設ける。

- Control API、管理DB、宣言していない秘密情報・認証情報へのアクセスを禁止する。
- 宣言していないネットワークアクセスを禁止する。
- ホスト側の機密ディレクトリ（本人の HOME、設定、キーチェーン、SSH エージェント）をマウントしない。
- Dockerソケットなど、管理権限につながるインターフェースを渡さない。
- CPU、メモリ、実行時間に上限を設ける。
- 前の段の Sandbox を次の段に使い回さない。

段ごとにネットワークポリシーを分ける（上の表）。

Docker等による隔離は有力だが、コンテナで実行するだけで安全になるわけではない。ファイル共有、ネットワーク、権限の設定まで含めて検証する。

GitHub 側の CI の扱い（未信頼のコードを実行する CI に秘密情報と書き込み権限を渡さないこと）は、software-engineer へ移した。

### 隔離の検証

隔離が実際に機能していることを、Phase 1の自動セキュリティテストで確かめる（14.2）。

例えば、段のプログラムや作業の段のコードに管理DBやControl APIへアクセスする処理を仕込み、隔離環境から実際にアクセスできないことを確認する。権限設定が正しいと思い込むのではなく、突破できないことをテストで確かめる。

## 15.8 承認と操作内容の結び付け（Phase 2）

承認は、次の情報と結び付ける（ハーネス契約 7.2、specs 02 の approvals）。

| 項目 | 例 |
| --- | --- |
| 操作の種類 | スペシャルハーネスが宣言した操作（例 `merge_pull_request`） |
| 対象 | 結果 JSON の `target`（表示用。例 リポジトリと PR 番号） |
| 中身の識別子（content_id） | スペシャルハーネスが決める、承認を求めたときの中身の識別子（開発なら PR の head commit SHA）。Evaloom は完全一致で比べるだけで、意味を解釈しない |
| 操作パラメータのハッシュ | 操作・対象・content_id を正規化した値 |
| 承認者 | 本人（管理画面） |
| 使用回数の上限 | 原則1回 |
| 有効期限 | 承認ごとに設定する |

出す段は、外へ出す操作の直前に、実物から求めた content_id を添えて Evaloom に問い合わせる。Evaloom は承認したときの content_id と比べる。

| 状況 | 扱い |
| --- | --- |
| 内容が一致する | 操作できる |
| content_id が変わった | 承認は無効 |
| 操作対象が変わった | 承認は無効 |
| 使用済み | 実行しない |
| 有効期限切れ | 再承認を求める |

- 承認の照合と消費はDBで原子的に管理する。
- 確かめたものと出すものが同じであることは、スペシャルハーネスが見張る。Evaloom が比べるのは、承認したときの content_id と出す直前の content_id だけである（本人決定 5）。
- 操作の結果が分からなくなった場合は、重複して実行する前に、外部システムの状態を照合する。照合できなければ、本人の判断待ちにする（ハーネス契約 7.5）。
- 外部システムの側での一致の確かめ方（開発なら GitHub のマージ API の `sha` パラメータ、ブランチ保護）は、スペシャルハーネスが決める（software-engineer へ移した）。

# 22. 設計思想

Evaloom は、Linear などから仕事を受け取り、どの Project またはスペシャルハーネスに頼むかを決めて振り分け、結果を返すオーケストラである。仕事そのもの（準備し、作業し、確かめ、出す）はスペシャルハーネスが行う（vision.md 1章）。

Evaloomは、単なるAI自動実行ツールではない。

**仕事の振り分け、本人の判断の一元化、段ごとの安全な場所、スペシャルハーネスの版の管理、コンテキスト管理を中心に置き、その上に AI 同士の協議、定量評価、継続的自己改善を重ねていく AI オーケストレーション基盤**である。

各スペシャルハーネスは独立して開発・管理され、複数の Project から共有できる。開発、X の運用、調査など、種類の違う仕事をスペシャルハーネスとして足していき、Evaloom の中心は変えない。

Evaloom はスペシャルハーネスの宣言（段、承認対象、鍵、受け入れ条件の要否）、版、使用モデル、評価、改善履歴を把握し、仕事を適切な振り分け先へ割り当てる。仕事の種類で中身が変わる処理はスペシャルハーネスに任せ、Evaloom は中身を解釈しない。

そして改善効果をAIの主観的な判断ではなく、再現可能なテストと実運用データに基づいて検証する。

これにより、今後登場する新しいAIモデル、ミクロハーネス、スペシャルハーネスを継続的に取り込み、検証し、採用できるAI組織の実現を目指す。

**最終目標は、使い続けるほど運用データが蓄積され、専門性と実行品質を検証可能な形で高められるAIプラットフォームを構築することである。**
