# Evaloom — システム基本仕様書

**バージョン：** 1.2（1.1 の確認事項 Q1〜Q22 への回答を反映）  
**ステータス：** 基本仕様確定・詳細設計前  
**対象環境：** macOS / Mac mini M4 Pro  
**主要技術：** React / TypeScript / Go  
**システム種別：** 評価駆動型AIオーケストレーションプラットフォーム

---

# 1. プロジェクト概要

## 1.1 システム名称

**Evaloom（エヴァルーム）**

Evaluate（評価）とLoom（織り合わせる）を組み合わせた名称。

複数のAIハーネスを連携させ、実行結果を評価しながら継続的に改善するAI組織を表す。

## 1.2 目的

Evaloomは、複数のAIハーネスを中央から統括し、外部サービスやユーザーから受け取ったタスクを、適切な専門ハーネスに振り分けるシステムである。

タスクの自動実行だけではなく、以下を統合的に管理する。

- 専門ハーネスの開発・登録・共有
- プロジェクトごとのハーネス適用
- コンテキスト管理
- AI同士の協議・相互レビュー
- タスク実行・状態管理
- 共通契約と中央テスト
- 分野別の定量評価
- 継続的な自己改善
- モデル更新に応じた最適化
- バージョン管理・承認・ロールバック

最終的には、各専門ハーネスが独立して作業しながら、中央システムが品質と改善を統制するAI組織の実現を目指す。

## 1.3 基本原則

1. 中央システムはタスク、ハーネス、プロジェクト、契約、評価、改善を統括する。
2. ハーネスと業務プロジェクトは独立したリポジトリとして管理する。
3. 複数プロジェクトから同じハーネスを共有できる。
4. プロジェクトごとに使用するHarness Profileのバージョンを固定できる。
5. 共通契約と評価基準には明確な正本を設ける。
6. すべての正式運用ハーネスは評価仕様を持つ。評価基盤ができるまでのハーネスは「暫定運用」として扱う（11.1）。
7. 改善案は比較実験と実運用データに基づいて採用する。
8. AI同士の協議は必要な場合のみ実行する。
9. コンテキストは責務ごとに分離し、必要な情報だけを渡す。
10. 重要操作は権限制御・監査・承認を必要とする。
11. 新モデルや新ハーネスを追加しても、中央システムを大幅に変更しない。
12. 評価不能な変更を自動的に本番適用しない。
13. 危険な操作は、AIへの禁止指示ではなく、AIの権限外に置くことで防ぐ。例えば「PRをマージしない」と指示するのではなく、ハーネスにマージの権限を持たせない。
14. AIが実行するコードだけでなく、AIが書き換えられるコードも信用しない（15.7）。
15. 実行・改善するAIと、その合否を決める仕組みを分ける。AIが合格基準を自分で変えて合格できる状態を作らない（8.5、11.6、12.3）。
16. 安全対策は、対象となるリスクと防止効果を明確にし、リスクの重大性と実装・運用コストを比較したうえで、必要十分な範囲で設計する。重大なリスクへの必須対策は省略しない。

# 2. システム全体構成

## 2.1 アーキテクチャ

Evaloomを以下のレイヤーで構成する。


| レイヤー                | 役割                                           |
| ------------------- | -------------------------------------------- |
| Event Layer         | 外部サービスや手動指示からのイベント受信                         |
| Control Layer       | プロジェクト解決、タスク分類、権限、ルーティング                     |
| Registry Layer      | プロジェクト、ハーネス、モデル、契約の管理                        |
| Context Layer       | Global / Harness / Project / Task Contextの管理 |
| Collaboration Layer | AI同士の協議、レビュー、成果物統合                           |
| Execution Layer     | ハーネス起動、実行監視、作業環境管理                           |
| Evaluation Layer    | ルーブリック評価、テスト、比較分析                            |
| Improvement Layer   | 改善提案、実験、採用、ロールバック                            |
| Management UI       | 監視、設定、評価、承認、履歴の表示                            |


各レイヤーは責務を明確に分離する。

中央オーケストレーターは各ハーネスの具体的な実装に直接依存せず、共通契約とAdapterを介して利用する。

## 2.2 技術スタック


| 領域         | 採用技術                       |
| ---------- | -------------------------- |
| フロントエンド    | React + Vite + TypeScript  |
| UI         | Tailwind CSS + shadcn/ui   |
| バックエンド     | Go                         |
| HTTP API   | Go標準 `net/http`            |
| リアルタイム通信   | Server-Sent Events（SSE）    |
| 初期データベース   | SQLite / WALモード            |
| 将来的なDB候補   | PostgreSQL                 |
| 非同期処理      | Go Worker + 永続ジョブ管理        |
| ハーネス接続     | CLI / SDK / 外部プロトコルAdapter |
| ソースコード管理   | Git / GitHub               |
| 作業環境       | Git worktree               |
| 初期実行ホスト    | Mac mini M4 Pro            |
| バックグラウンド起動 | launchd                    |
| 初期利用範囲     | Mac mini本体からの接続のみ（ループバック）。別の端末・遠隔からの接続は認証導入後（15.5） |
| Webhook受信   | 署名検証付きの公開HTTPSエンドポイント経由（Mac miniのポートは直接公開しない） |
| 通知         | Linearコメント＋macOS通知（将来Slack・スマートフォンを追加可能にする） |


ライブラリの具体的なバージョンは詳細設計時に検証して固定する。

## 2.3 デプロイ方針

初期段階では、React管理画面、Go API、Runner、SQLiteをMac mini上で稼働させる。

Goバックエンドは管理画面とは独立して常駐する。

将来の分散実行を考慮し、Runnerを論理的に独立したコンポーネントとして設計する。

RunnerはControl Planeへ自分から仕事を取りに行く方式（pull）とする。Control PlaneからRunnerへは接続しない。Runnerを別のマシンに置いても、外からRunnerへ接続する必要がない。

Control Planeを別サーバーへ移設しても、各Runnerの設定を更新することで実行先を切り替えられる構成とする。

# 3. GitHub・ディレクトリ管理

## 3.1 基本方針

Evaloom本体、各ハーネス、各業務プロジェクトは、原則として独立したGitHubリポジトリで管理する。

中央システム配下にすべてのプロジェクトを配置する必要はない。

GitHub管理の対象は以下とする。

- ソースコード
- 仕様書
- 設計資料
- 共通契約
- プロンプト
- Skills
- テストコード
- 評価基準
- Harness Profile定義
- 非機密の構成ファイル

以下は原則としてGitHubへコミットしない。

- APIキー
- 認証トークン
- 秘密鍵
- 実行中のSQLiteデータベース
- 機密性を含む実行ログ
- 一時worktree
- 顧客の秘密情報

必要な履歴はDBや別の適切なストレージに保存する。

## 3.2 推奨ディレクトリ構成

```
~/
├── evaloom/
│   ├── frontend/
│   ├── backend/
│   ├── contracts/
│   ├── evaluations/
│   ├── context/
│   ├── configs/
│   └── docs/
│
├── harnesses/
│   ├── claude-developer/
│   ├── codex-developer/
│   ├── custom-research/
│   └── document-agent/
│
├── projects/
│   ├── customer-system/
│   ├── corporate-site/
│   └── internal-tool/
│
└── ai-workspaces/
    ├── task-001/
    └── task-002/
```

これは推奨配置例であり、配置場所を強制しない。

既存プロジェクトの移動は不要とする。

## 3.3 パス管理

各リソースを以下の情報で識別する。

- Project ID
- Harness ID
- Runner ID
- Local Repository Path
- Git Repository URL
- Base Branch
- Context Location
- Worktree Root

Registryへパスを登録する際には、存在確認、アクセス権限、Gitリポジトリの妥当性を検証する。

AIに実行先パスを推測させない。

## 3.4 リポジトリ間の依存関係

ハーネスをプロジェクトに適用する際、ハーネスのソースコードをプロジェクト内にコピーしない。

中央のHarness RegistryとProject Registryによって参照関係を管理する。

使用するHarness ProfileはSemVerのバージョンで固定する。各バージョンには実体のGit commit SHAを記録する（5.4）。

共有ハーネスの更新が、利用中のすべてのプロジェクトへ無条件に反映されることを防ぐ。

# 4. プロジェクト・ハーネスの共有

## 4.1 目的

同じ専門ハーネスを複数の業務プロジェクトから利用可能にする。

例えば、`custom-research`をProject AとProject Bの双方から利用できるようにする。

## 4.2 適用方式

Project Registryに使用するHarness Profileを関連付ける。

構成例：

```
projectId: project-a

repository:
  runnerId: mac-mini
  path: /Users/orion/projects/project-a
  baseBranch: develop

harnesses:
  developer:
    harnessId: claude-developer
    profileVersion: "1.2.0"

  researcher:
    harnessId: custom-research
    profileVersion: "2.0.0"
```

これはEvaloom独自の設定仕様案である。

実行時、Evaloomは対応するProfileを解決し、対象プロジェクトのコンテキストと組み合わせてハーネスを起動する。

## 4.3 バージョン固定

プロジェクトごとに使用Profileを固定できる。

例：


| プロジェクト    | ハーネス             | Profile |
| --------- | ---------------- | ------- |
| Project A | Claude Developer | 1.2.0   |
| Project B | Claude Developer | 1.3.0   |
| Project A | Custom Research  | 2.0.0   |
| Project C | Custom Research  | 1.8.0   |


新しいProfileは既存Profileを上書きせず、独立した変更候補として管理する。

## 4.4 ハーネス更新

共有ハーネスが改善された場合、以下を実行する。

1. 新Profile生成
2. 共通契約テスト
3. ハーネス固有テスト
4. 影響プロジェクトの検出
5. 代表プロジェクトによる検証
6. 必要に応じて14日間の評価
7. 採用判断
8. プロジェクトごとのProfile更新

影響プロジェクトへの無条件な一括反映は禁止する。

# 5. Registry管理

## 5.1 Project Registry

保持情報：

- Project ID
- 名称
- Local Repository Path
- Git Repository URL
- Runner ID
- Base Branch
- Linear Team ID
- Linear Routing Label
- Default Harness
- Review Harness
- Context Location
- テストコマンド
- セットアップコマンド（worktree作成後に実行する）
- worktreeへコピーするファイルの許可リスト
- 許可操作
- 承認ポリシー

`.env`などのファイルは無条件にコピーしない。許可リストに載っていないファイルはworktreeへコピーしない。

## 5.2 Harness Registry

保持情報：

- Harness ID
- 名称
- 専門分野
- 対応タスク
- 対応モデル
- Adapter
- 実行方式
- 利用可能ツール
- Tool Permissions
- Input / Output Contract
- Harness Version
- Prompt Version
- Skill Version
- Evaluation Policy
- Improvement History

## 5.3 Model Registry

保持情報：

- Provider
- 正式なModel ID
- 対応する実行環境
- コンテキスト制限
- ツール利用能力
- 推論設定
- 料金情報
- 公式参照元
- 確認日時
- 対応Harness Profile

モデルの表示名と実際のModel IDを区別する。

## 5.4 Harness Profile

Harness Profileは以下を一体として定義する。

```
Harness Profile
├── Harness Version
├── Model ID
├── Prompt Version
├── Skill Versions
├── Tool Configuration
├── Context Policy Version
├── Execution Configuration
├── Collaboration Policy
└── Evaluation Policy Version
```

モデルが異なれば、同じ役割であっても異なるProfileを設定できる。

### バージョンと再現性

- Profileの表示バージョンにはSemVer（例 `1.2.0`）を使い、これを正本とする。
- 各バージョンの実体はGit commit SHAとともに記録する。
- 公開済みのタグの付け替えを禁止する。
- 同じProfileバージョンからは、常に同じ定義を読み込めるようにする。

### 状態

評価仕様を持たないProfileは「暫定運用」とし、評価仕様を備えた時点で正式運用へ移す（11.1）。

# 6. Linear連携

## 6.1 基本方針

Linear Projectを必須の識別子としない。

標準方式は、**Linear Team + Issue Labelによるルーティング**とする。

Linear Projectを利用したルーティングは任意機能として残す。

## 6.2 Label構成

推奨例：

- `repo:customer-system`
- `repo:corporate-site`
- `repo:internal-tool`
- `ai-ready`

`repo:*`が実行先プロジェクトを示す。

`ai-ready`が付与された時点を自動実行トリガーとする。`ai-ready`が付いたままのIssueが更新されても、再び起動しない。

`ai-ready`が外された場合、またはIssueがキャンセルされた場合は、そのIssueの待機中・実行中のタスクを中止する。

## 6.3 ルーティング処理

1. Linear Webhook受信
2. 署名検証
3. イベント重複排除
4. Team ID確認
5. Issue Label取得
6. 登録済みProject IDとの照合
7. Task生成
8. 実行キュー登録

複数の実行先Labelがある場合や、未登録Labelの場合は自動実行せず、タスクをBlockedにする。

受け入れ条件が書かれていないIssueも実行せずBlockedにし、Linearへ受け入れ条件の記入を求めるコメントを返す。

## 6.4 実行結果の返却

処理完了後、該当Issueへ次の情報を返す。

- 実行ステータス
- 実行担当ハーネス
- 作業概要
- 検証結果
- PR URL
- エラー情報
- 必要な承認事項

Evaloom自身によるIssue更新が再び同じジョブを起動しないようにする。

## 6.5 保存期間への配慮

LinearのIssue保存・アーカイブと料金プランによる制限を考慮する。

Linear Projectの使用を強制せず、Issueをタスク入力元として利用できる設計とする。

長期的な実行履歴と評価データはEvaloom側に保持し、Linearの保存状態へ依存しない。

Linearの料金枠・アーカイブ仕様は運用開始時に公式情報と実環境で確認する。

## 6.6 接続方式

- GraphQL APIの読み書きには個人APIキーを使う（Phase 2）。
- Webhookの受信には、APIキーとは別の署名シークレットを使って署名を検証する。
- Mac miniのローカルHTTPポートは直接公開しない。署名検証付きの公開HTTPSエンドポイントを経由してイベントを受け取る。

# 7. コンテキスト管理

## 7.1 4階層構成

コンテキストは以下の4階層で管理する。

### Global Context

Evaloom全体の共通情報。

- 組織運用ルール
- 共通契約
- セキュリティポリシー
- テスト方針
- 評価方針
- 権限・承認ルール

### Harness Context

ハーネス固有の情報。

- 専門領域
- モデル向け指示
- プロンプト
- Skills
- ツール使用方針
- 得意・不得意な処理
- 過去の改善結果

### Project Context

プロジェクト固有の情報。

- プロジェクト目的
- 技術スタック
- アーキテクチャ
- コーディング規約
- 設計判断
- テスト仕様
- 既知の制約

Phase 1では、各プロジェクトリポジトリの`AGENTS.md`をProject Contextの正本とする。Evaloom側でProject Contextを管理する仕組みは後のPhaseで追加する。

`AGENTS.md`の固定は次のとおりとする。

- 実行開始時に、worktreeの開始点のcommitに含まれる、適用対象の`AGENTS.md`をすべて特定する。ルートだけでなく、サブディレクトリの`AGENTS.md`も対象とする。
- 特定したファイルの内容とハッシュを、実行履歴に保存する。
- 実行途中に`AGENTS.md`が変更されても、そのExecutionの確定済みの指示としては自動採用しない。
- Claude Code固有の指示ファイルやハーネスの設定についても、実行開始時の構成を同様に記録する。

### Task Context

タスク固有の情報。

- Issue内容
- 受け入れ条件
- 作業計画
- 実行状況
- 実行ログ
- 検証結果
- 未解決事項

## 7.2 Context Builder

中央でContext Builderを提供する。

実行時に必要な情報を抽出し、Execution Contextを生成する。

処理には以下を含む。

- Context取得
- 関連情報の選択
- バージョン確認
- 優先順位判定
- 権限確認
- 情報量調整
- 実行先向けの整形

すべてのコンテキストを毎回渡すことは禁止する。

## 7.3 コンテキスト優先順位

Globalの安全・権限ルールは下位階層で上書きできない。

Harness ContextとProject Contextが矛盾した場合、情報の種類と権限に応じて解決する。

解決できない重要な矛盾がある場合は実行せず、タスクをBlockedにする。

## 7.4 Context更新管理

ハーネスが発見した情報は更新候補として提出する。

中央が根拠・既存情報との整合性・影響範囲を確認し、承認されたものだけを正式反映する。

## 7.5 ハーネスの設定環境の分離

Evaloomから起動するハーネスには、専用の設定環境を設ける。

本人のグローバル設定（`~/.claude/CLAUDE.md`、`~/.codex/AGENTS.md`など）や個人メモリを、意図せず読み込ませない。

ハーネスが実際に読み込んだ指示を検証するテストを用意する（14.2）。

# 8. タスクオーケストレーション

## 8.1 イベント入力

初期対応：

- React管理画面からの手動指示
- Linear Webhook

Phase 1で扱うのは開発タスク（コード変更とPR作成）だけとする。調査・文書タスクは後のPhaseで扱う。

管理画面から手動でタスクを作る場合も、受け入れ条件を必須の入力項目とする（9.5）。

将来的な対応：

- Gmail
- GitHub
- Google Drive
- Slack
- Cron
- 外部API

## 8.2 タスク処理フロー

1. イベント受信
2. 認証・署名確認
3. 重複排除
4. プロジェクト特定
5. Context取得
6. タスク分類
7. Harness選択
8. Collaboration Mode判定
9. Worktree準備
10. Harness実行（commitまで）
11. テスト・検証
12. push・PR作成
13. 評価
14. 必要に応じた承認
15. 結果返却
16. 履歴保存

Phase 1では6のタスク分類を行わず、プロジェクトのDefault Harnessで実行する。

AI協議を導入するPhase 5までは、8のCollaboration ModeをSoloに固定する。

14の承認は、実行結果に対する承認である。15.3の承認対象操作は、その操作を行う直前に承認を必須とし、事後承認にしない（15.3）。

タスクの分解（task_steps）はPhase 1では使わない。

## 8.3 タスク状態

- Received
- Planning
- Queued
- Running
- Verifying
- Waiting Approval
- Completed
- Failed
- Cancelled
- Timed Out
- Blocked

ジョブの状態は永続化する。

再起動後も未完了タスクを検出できるようにする。

### 状態の扱い

- Linearルーティングで保留したタスクと、受け入れ条件のないタスクはBlockedにする（6.3）。
- 1つのタスクに複数のExecutionを紐付けられる構成とする。再実行は、同じタスクに新しいExecutionを追加する。
- システム再起動で中断されたExecutionは失敗（中断）として記録し、タスクをFailedにする。作業中だったworktreeは保持する。
- 中断・失敗したタスクを自動では再実行しない（自動リトライは0回）。本人が確認した後に、新しいExecutionを生成する。再実行時のGit作業の扱いは8.5に従う。
- 使用するProfileとContextの版は、Runnerがタスクを取得した時点でExecutionに固定する。実行開始後に割り当てやContextが変わっても、そのExecutionでは切り替えない。
- Project Context（`AGENTS.md`）は、worktreeの開始点のcommitに含まれるものを使う。固定の方法は7.1に従う。

## 8.4 Local Runner

Local RunnerはControl Planeから仕事を取りに行く（pull、2.3）。

役割：

- Worktree作成
- 作業ディレクトリ設定
- Harness Adapter起動
- プロセス監視
- ログ収集

## 8.5 Git作業の出口

- ハーネスはcommitまでを行う。pushとPR作成はRunnerが行う。
- 登録された必須の検証がすべて成功した場合だけ、pushとPR作成へ進む。テストの失敗、テストコマンドの未設定、検証できない場合は、失敗の理由と作業結果を保存して止める。
- テストコマンドはProject Registry（Evaloom側）の登録を正本とする。ハーネスはテストコマンドを変更できない。

### テストの弱体化への対策

テストのファイルはハーネスが編集できるリポジトリの中にある。そのため、ハーネスがテストを削除・無効化・弱体化すると、検証が通ってしまう。Runnerは次のGate 2とGate 3で検証し、残りの範囲はPRのレビューで本人が確認する。

テストの変更を差分から判定する検査（旧Gate 1）は、Evaloom本体に持たせない（Q36）。差分のファイル名などで判定する方式はテストの道具や設定ファイルの種類だけ列挙が要り、開発に固有の判定を本体に増やすことになるためである。Gateの番号は既存の記録と合わせるため変えず、Gate 1は欠番とする。

**Gate 2：通常のテストを1回実行する**

- Project Registryに登録したテストコマンドを、Test Sandboxで1回実行する。
- 成功・失敗だけでなく、作業開始時点の既存テストが欠けずに実行されたかを確認する。新しいテストを追加すれば実行数は増えるため、前回との件数の一致では判定しない。
- テストランナーが実行したテストのIDを出力できる場合は、既存テストのIDがすべて実行されたことを照合する。IDが取れない環境では実行数とskip数で確認するが、それだけでは既存テストが欠けていないことを完全には証明できない。
- 既存のテストが残っていても、実際に実行されたとは限らない（例：新しく追加したテストの`describe.only`によって、ほかのテストが実行されなくなる）。そのため、実行数の確認を必須とする。
- 作業開始時点の既存テストを別に固定して再実行する仕組みは、Phase 1では作らない。既存テストの欠けはGate 2のIDの照合で検出し、既存テストの中身の変更はPRのレビューで本人が確認する。

**Gate 3：実行結果とcommitの検証**

- 検証したcommitのSHAとpushするcommitのSHAが一致すること、作業ツリーに未コミットの変更が無いこと、必要なテストが実際に実行されたことを確かめる（上記の検証とpushの順序）。
- GitHubの必須ステータスチェックでは`skipped`や`neutral`も条件を満たしたと扱われる場合がある。そのため、必要なテストが実際に実行されたかは、Evaloom側で確かめる。

**共通の扱い**

- 止まったタスクは、本人が変更内容を確認し、続行を選んだ場合だけ先へ進む。
- 検証できない場合は、Blockedにする。自動でpushとPR作成を行わない。
- 既存テストの期待値やassertionの書き換え、テストの実行設定・CIの定義の変更、アプリのコードにテストのときだけ通る抜け道を作る変更は、Phase 1の仕組みでは検出しない。この範囲はPRのレビューで本人が確認する。Phase 3以降は、AIが変更できない場所に置く非公開の受け入れテスト（11.6）と評価AIで扱う。
- 検証とpushは、次の順序で行う。
  1. ハーネスがコードを変更し、commitする。
  2. RunnerがそのcommitのSHAを取得し、記録する。
  3. RunnerがTest Sandboxで、そのcommitに対してテストを実行する（15.7）。
  4. Runnerが、HEADが記録したSHAと一致すること、作業ツリーに未コミットの変更が無いことを確認する。
  5. Git Publisherが同じcommitをpushし、PRを作成する（15.7）。
- テストの後にcommitが追加された場合や、作業ツリーに変更が残っている場合は、pushせずに止める。
- GitHub側でも、PRの最新commitに対してCIを実行し、必須ステータスチェックで最新commitのSHAの成功を求める。このCIも未信頼のコードを実行するものとして扱う（15.7）。
- SHAと作業ツリーの一致で確かめられるのはコードの一致までである。テスト環境や外部依存まで含めた完全な再現性は保証しない。
- ブランチ名は`evaloom/<task-id>-<短い名前>`とする。
- 1つのタスクにつき、アクティブなPRは最大1本とする。
- PRのマージは承認対象とする（15.3）。
- 承認の仕組みを導入するPhase 2までは、本人がGitHub上でPRをマージする。EvaloomはPRをマージしない。
- Phase 2以降は、承認ポリシーでPRマージを承認対象から外したProjectに限り、必須の検証をすべて通ったcommitを、Git Publisherがベースブランチへfast-forwardでpushする。このProjectではPRを作らない（15.3）。

### 再実行時の扱い

- 原則として、前回のブランチ・worktree・PRを引き継ぐ。
- 再実行の前に、Gitの状態と未コミットの変更を確認する。
- 既存のPRが開いている場合は、同じブランチに追加commitする。PRがまだない場合は、作業完了後に作成する。
- 既存のPRがクローズ済みの場合は、通常の再実行を受け付けない。本人が明示的に最初からやり直すことを選んだ場合だけ、新しいブランチで実行する。
- 既存のPRがマージ済みの場合は、原則として新しいタスクを作る。評価結果や実装履歴が前のタスクと混ざらないようにするためである。
- 最初からやり直す場合は、本人が明示的に選ぶ。
- やり直す場合も過去の作業履歴は保持する。既存のPRがあれば、クローズするなどして整理する。

## 8.6 Worktreeの環境構築

- 新しくworktreeを作るときは、リモートのBase Branchを取得し、そのcommit SHAを記録して開始点にする。
- worktree作成後、Project RegistryのセットアップコマンドをTest Sandboxで実行する。ホスト上では直接実行しない（15.7）。
- `.env`などのファイルは無条件にコピーしない。Project Registryの許可リストに載ったファイルだけをコピーする。
- 許可リストには、秘密情報を含まないファイルだけを載せる。テストに値が必要な場合は、テスト専用のダミーの値を使う（15.6）。

## 8.7 同時実行

- 同時に実行するタスクは全体で2本までとする。
- 同じプロジェクトのタスクは1本ずつ実行する。
- 上限を超えたタスクはQueuedで待つ。

## 8.8 通知

- 承認待ちなど、本人の対応が必要なときに通知する。
- 承認の仕組みが無いPhase 1では、タスクの完了と失敗を通知する。
- 初期段階の通知先はLinearコメントとmacOS通知とする。
- 将来的にSlackやスマートフォンへ届く通知経路を追加できる構成にする。

改善の検証はオフラインのベンチマークを主にする。

実運用での試験は期間を区切り、現行版と候補を切り替えて行う。同じタスクを現行版と候補で二重に実行しない。

ただし、必要な評価件数は実験内容や結果のばらつきによって調整する。件数の条件は、Phase 4に入る時点の実績を見て決める。

## 12.5 比較指標

- 品質スコア
- 要件充足率
- テスト成功率
- 差し戻し率
- 実行時間
- 費用
- 手戻り
- 人間の修正負担
- 安全性
- 実行安定性

改善効果が十分に確認できない場合は判定保留とする。

### 指標の定義

| 指標 | 定義 |
| --- | --- |
| 差し戻し率 | レビューを受けたPRのうち、変更要求が発生したPRの割合 |
| 差し戻し回数 | PRごとの変更要求の回数 |
| 人間の修正負担 | 人間による追加修正コミット、その変更行数、手動介入の回数。可能なら実際の修正時間も記録する |
| 費用 | トークン数と実行時間で記録する。金額はAPI利用時だけ記録する |

変更行数だけでは修正負担を正確に測れないため、人間の修正負担は複数の指標で評価する。

## 12.6 バージョン管理

現行Profileと改善候補を独立して保持する。

どのプロジェクトがどのProfileを使用していたかを追跡する。

正式採用後も旧版を保持し、ロールバック可能にする。

# 15. Security &amp; Policy

## 15.1 基本方針

外部イベント・メール・Webページ・Issue本文を信頼済みシステム命令として扱わない。

セキュリティ設計では、次の原則を守る。

| 原則 | 内容 |
| --- | --- |
| Untrusted Code Execution | ハーネスが生成・変更できるコードは、セットアップやテストも含めて隔離環境で実行する（15.7） |
| Privilege Separation | 本人、Trusted Runner、ハーネスの権限を分ける（15.5、15.7） |
| Approval Binding | 承認は、操作・対象・内容の版に結び付ける（15.8） |
| One-Time Authorization | 承認は原則として1回限りとする（15.8） |
| Fail Closed | 認証・承認・検証のどれかに失敗したら、操作を実行しない |

## 15.2 必須対策

- Webhook署名検証
- イベント重複排除
- 循環トリガー防止
- 許可済み実行パス
- タスク単位の権限
- 実行環境の分離
- シークレット管理
- ログの機密情報除外
- タイムアウト
- 費用上限
- 監査ログ
- 重要操作の承認

## 15.3 承認対象

原則として以下を承認対象とする。

- 本番環境へのデプロイ
- PRマージ
- 外部メール送信
- 重要ファイル削除
- 認証・権限変更
- 共通契約の変更
- 評価基準の変更
- 中央セキュリティポリシー変更

承認対象操作は、その操作を行う直前に承認を必須とする。事後承認にはしない。

権限と承認状態は、実行開始時だけでなく、副作用のある操作を実際に行う直前にも確認する。

承認の仕組みを導入するPhase 2までは、Evaloomとハーネスは上記の操作を実行しない。これは指示で禁じるのではなく、Runnerの実行権限によって拒否する（15.7）。PRのマージは本人がGitHub上で行う（8.5）。

Phase 2以降、本人はProjectの承認ポリシーで、PRマージを承認対象から外せる。外したProjectでは、8.5の必須の検証（Gate 2・3）をすべて通ったcommitを、PRを経ずにベースブランチへpushする。既定は承認対象のままとし、外せるのはPRマージだけとする。外したProjectでは、8.5でPRのレビューに任せている範囲（既存テストの書き換え、テストの実行設定・CIの定義の変更など）を確認する人がいなくなる。そのため外せるのは、この確認を省いてよいProjectに限る。ほかの承認対象操作は外せない。GitHub側では、外したProjectのリポジトリに限り、Git Publisherの認証情報にベースブランチの更新を許す。

ただし、Phase 1でも本人は、管理画面からProject RegistryやHarness Registryの権限設定（許可操作、承認ポリシー、Tool Permissionsなど）を変更できる。Runnerとハーネスには、権限設定を変更する操作を許可しない。

## 15.4 Git作業環境

通常のローカルリポジトリを直接変更せず、専用worktreeを使用する。

worktreeはOSレベルの隔離ではないため、高リスク作業には別ユーザーやコンテナ等による分離を検討する。

## 15.5 利用者・認証・承認者

- 利用者は本人1人とする。Phase 1では利用者管理の仕組みを作らない。
- 利用者管理を作らないことと、タスクの実行権限を制限しないことは別である。タスク単位の実行権限の制限はPhase 1から必須とする（15.2）。
- 単一ユーザー運用は、外部からの無認証アクセスを許すという意味ではない。
- Phase 1の管理画面とControl APIは、Mac miniのループバック（127.0.0.1）からの接続に限定する。
- MacBook Air、Windows、スマートフォンなど別の端末からのアクセスは、認証・認可と通信経路の保護を実装した後に対応する。将来はTailscaleなどを使った安全なリモートアクセスを想定する。
- 承認は本人だけが実施できるようにする。
- 本人・Trusted Runner・ハーネスの3つの権限境界を、正式な設計要件とする。
- 本人用APIはループバックで公開されるため、同じマシンで動く不正なプログラムからのアクセスも考慮する。本人用APIには認証とCSRF対策を設ける。
- Runnerは、本人用とは別の限定された認証方式を使う。
- ハーネスには、本人用とRunner用のどちらの認証情報も渡さない。

## 15.6 秘密情報の扱い

- 秘密情報はGitに含めない。
- Harness Sandbox、Test Sandbox、ハーネスが変更できるコードで動くCIには、本物の秘密情報を一切渡さない。管理用の認証情報だけでなく、プロジェクトのAPIキーや`.env`の中身も渡さない。
- テストに値が必要な場合は、テスト専用のダミーの値を使う。
- 本物の秘密情報を使うのは、Trusted RunnerとGit Publisherの中だけとする。用途は、pushやPR作成などEvaloom自身の操作に限る。
- worktreeへコピーするファイルは、秘密情報を含まないものだけを許可リストで管理する（5.1、8.6）。
- 例外として、ハーネスがモデルAPIへ接続するための認証情報がある。これはサンドボックスの外で付与し（認証を付けるプロキシなど）、ハーネスから値が見えないようにすることを原則とする。CLIの仕組み上それができない場合に限り、Evaloom専用で、用途と利用上限を絞った認証情報を渡す。

## 15.7 実行権限の境界

Phase 1から、次の権限境界を必須とする。

| 構成要素 | 実行内容 | 権限 |
| --- | --- | --- |
| Control API | 本人用のAPIとRunner専用のAPIを分ける | それぞれ別の認証情報で操作する |
| Trusted Runner | ジョブ管理、隔離環境の作成、成果物の検証 | 限定された管理権限 |
| Harness Sandbox | AI（Codex・Claude Code）によるコード変更 | プロジェクト単位で制限する。許可済みのworktreeだけを編集できる。秘密情報を渡さない（15.6） |
| Test Sandbox | セットアップとテストの実行 | 秘密情報（管理用・プロジェクト用とも）を渡さない（15.6） |
| Git Publisher | 検証済みcommitのpushとPR作成 | 対象リポジトリに限った権限 |

- `127.0.0.1`に限定しても、同じMac mini上のハーネスからはHTTPリクエストを送れる。そのため、接続元の制限だけでは権限境界にならない。
- 同じmacOSユーザーで動かす場合、APIトークンを別ファイルに置くだけでは隔離にならない。
- Runnerは、リポジトリ由来のスクリプトをホスト上で直接実行しない。セットアップコマンド（`go generate`、`composer install`など）やテストも隔離の対象とする。依存関係のインストール時に任意のスクリプトが実行される可能性があるためである。

### 隔離の条件

Harness SandboxとTest Sandboxには、次の条件を設ける。

- Control API、管理DB、秘密情報・認証情報へのアクセスを禁止する。
- 不要なネットワークアクセスを禁止する。
- ホスト側の機密ディレクトリをマウントしない。
- Dockerソケットなど、管理権限につながるインターフェースを渡さない。
- CPU、メモリ、実行時間に上限を設ける。

CodexやClaude CodeはモデルAPIへの通信が必要な場合があるため、ハーネス実行用とテスト実行用でネットワークポリシーを分ける。

Docker等による隔離は有力だが、コンテナで実行するだけで安全になるわけではない。ファイル共有、ネットワーク、権限の設定まで含めて検証する。

### GitHub側のCI

ハーネスはCIの定義やテストを変更できる。そのため、PRに対して動くCIも未信頼のコードを実行するものとして扱う。

- ハーネスが変更できるコードで動くCIには、秘密情報、リポジトリへの書き込み権限、デプロイの権限を渡さない。
- CIの定義の変更は、PRのレビューで本人が確認する（8.5）。

### 隔離の検証

隔離が実際に機能していることを、Phase 1の自動セキュリティテストで確かめる（14.2）。

例えば、テストスクリプトに管理DBやControl APIへアクセスする処理を仕込み、隔離環境から実際にアクセスできないことを確認する。権限設定が正しいと思い込むのではなく、突破できないことをテストで確かめる。

## 15.8 承認と操作内容の結び付け（Phase 2）

承認は、次の情報と結び付ける。

| 項目 | 例 |
| --- | --- |
| 操作の種類 | `merge_pull_request` |
| 対象 | リポジトリ、PR番号、対象ブランチ |
| 内容の版 | PRのhead commit SHA |
| 操作パラメータのハッシュ | 操作内容を一意に表す値 |
| 承認者 | 本人 |
| 使用回数の上限 | 原則1回 |
| 有効期限 | 承認ごとに設定する |

操作の直前に、現在の対象と承認の内容を比べる。

| 状況 | 扱い |
| --- | --- |
| 内容が一致する | 操作できる |
| commit SHAが変わった | 承認は無効 |
| 操作対象が変わった | 承認は無効 |
| 使用済み | 実行しない |
| 有効期限切れ | 再承認を求める |

- 承認の消費はDBで原子的に管理する。
- 操作の結果が分からなくなった場合は、重複して実行する前に、外部システムの状態を照合する。
- PRのマージでは、GitHubのマージAPIの`sha`パラメータでPRのHEADとの一致を求める。ただし、これだけではベースブランチの変更までは防げないため、ブランチ保護やマージキューと組み合わせる。

# 22. 設計思想

Evaloomは、単なるAI自動実行ツールではない。

**中央統制、専門ハーネス、コンテキスト管理、AI同士の協議、定量評価、継続的自己改善を統合したAIオーケストレーション基盤**である。

各専門ハーネスは独立して開発・管理され、複数の業務プロジェクトから共有できる。

中央システムはハーネスの能力、契約、使用モデル、評価、改善履歴を把握し、必要なタスクへ適切に割り当てる。

そして改善効果をAIの主観的な判断ではなく、再現可能なテストと実運用データに基づいて検証する。

これにより、今後登場する新しいAIモデルやハーネスを継続的に取り込み、検証し、採用できるAI組織の実現を目指す。

**最終目標は、使い続けるほど運用データが蓄積され、専門性と実行品質を検証可能な形で高められるAIプラットフォームを構築することである。**
